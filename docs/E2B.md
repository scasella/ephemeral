# E2B runtime and cleanup

Live mode requires `E2B_API_KEY`, an explicit custom `E2B_TEMPLATE_ID`, and a public HTTPS gateway URL. The control plane never falls back to E2B's default template. `SESSION_MAX_HOURS=1` is the default and supports an E2B Hobby account: every session ends within one hour and extensions are disabled in both the server and UI. Set `SESSION_MAX_HOURS=4` only after enabling E2B Pro. E2B documents a one-hour Hobby limit and a 24-hour Pro limit in its [pricing page](https://e2b.dev/pricing); this app enforces the smaller operator-selected maximum.

## Build a fresh template

For named Base, Node.js and Python toolchains, see [environment profiles](ENVIRONMENTS.md). The shared recipe supports offline inspection with `--profile base|node|python --dry-run` and an optional `--tag` for operator-run release builds. Profile selections do not reuse authenticated workspaces or pin an immutable provider build.

`sandbox/build-template.ts` uses the current [E2B Template SDK](https://changelog.e2b.dev/resources/introducing-build-system-2-0). It installs Node/npm, Git, Python3, tmux, pnpm, procps and Codex CLI, creates or validates the `user` account at `/home/user`, forces file-based ChatGPT credential storage, and checks that no Codex authentication file exists. Python3 provides descriptor-relative, symlink-safe reads for change review; the template explicitly checks its version. Older templates without Python3 return an unknown inspection result rather than falling back to unsafe file reads. It omits custom CPU/RAM so Hobby uses the account's default compute. It safely loads `.env` without overriding the existing environment or printing keys.

The default versions in `sandbox/runtime-versions.ts` are Codex CLI **0.162.1** and pnpm **12.11.2**, checked against their public npm registry metadata on 2026-10-14. The Node 24 Bookworm image is pinned by Docker registry digest. Exact package versions and the image digest are fixed; Debian apt packages still resolve from their current repository. Metadata and local template serialization were validated; a successful provider build/live session is still required to validate the Linux runtime. The Codex Linux x64 package expands to about 452 MB, so the template needs adequate disk space. Optional platform packages are explicitly included by npm.

```sh
# Local serialization only: does not require a key or create a resource.
npm run template:build -- --dry-run
# Operator-coordinated provider build: consumes E2B resources.
npm run template:build
# Read-only account/template preflight; creates/resumes nothing.
node --import tsx scripts/e2b-preflight.ts
```

Save the printed template ID as `E2B_TEMPLATE_ID` in the server deployment, then repeat the preflight. It authenticates via a sandbox listing, finds the accessible custom template across all pages, resolves its requested/default tag and checks the exact build status. Account access can be checked before a template ID exists. Output contains check results, not API keys or raw provider responses. The preflight cannot establish account billing plan/credits, sandbox tool behavior, or VM-to-gateway reachability without additional live evidence. The public SDK/API exposes usage metrics, not an authoritative plan/limit field.

To override pinned versions use `E2B_TEMPLATE_CODEX_VERSION` and `E2B_TEMPLATE_PNPM_VERSION` with exact versions; these names avoid the host Codex app's own `CODEX_VERSION` environment variable. `E2B_TEMPLATE_ALIAS` defaults to `ephemeral-codex`, and `E2B_BASE_IMAGE` can select another approved immutable digest. Building a template consumes provider resources; the server does not build one automatically. Never bake `.codex/auth.json`, API keys, repositories, or user workspace snapshots into the template. Deploy the application with Node 24 (repository engine requirement); E2B 2.56.0 itself requires at least Node 22.19.

As checked on 2026-10-14, [E2B pricing](https://e2b.dev/pricing) lists Hobby with $100 one-time credits, one-hour sessions and default CPU/RAM; Pro is $150/month plus usage and permits custom compute/longer sessions. Compute rates are $0.000014 per vCPU-second and $0.0000045 per GiB-second. The actual template allocation is reported by preflight rather than assumed. For example, 2 vCPU + 4 GiB costs about $0.1656 per running hour; 2 vCPU + 2 GiB would cost $0.1332/hour if supported by the selected plan. These are arithmetic estimates excluding plan fees and other billable provider operations. Building remains coordinated separately from read-only checks.

Each new VM has a fresh clone in `/home/user/workspace`, a unique `ephemeral/<session UUID>` branch, and a detached `ephemeral` tmux session that runs `codex login --device-auth` and launches Codex after a successful login. The browser displays the device sign-in inside that VM. Codex uses the user's own account; Ephemeral does not provide an OpenAI API key. The application does not copy or reuse another session's Codex auth. Codex exit or failed login leaves an interactive shell. Closing the browser detaches its PTY; tmux and the VM keep running until stop or expiry.

Before the live sign-in, enable device code login in your ChatGPT security settings or workspace permissions. The [official OpenAI authentication documentation](https://developers.openai.com/codex/auth) describes this prerequisite and the headless flow. The user must complete the displayed device code in their browser. If login is unavailable or expires, the VM remains accessible through its shell and can run a fresh `codex login --device-auth`; the application does not copy a host auth cache as a fallback.

The sandbox receives only a session-scoped Git gateway credential. Git reads it through a helper, with exact protocol/host/path matching and `credential.useHttpPath=true`; the credential never appears in clone URLs or command text. The gateway remote is `/gateway/git/<session UUID>.git`. Upstream GitHub tokens, E2B API keys and envd credentials remain on the server. The template must permit the control plane to run commands as `root` to terminate workspace processes during cleanup. `secure:true` is passed to the SDK (current SDKs secure envd automatically), and `network.allowPublicTraffic:false` requires authentication on sandbox public URLs. This is authenticated ingress, not a promise that ports cannot exist. See the [official SDK network options](https://github.com/e2b-dev/E2B/blob/main/packages/js-sdk/src/sandbox/sandboxApi.ts). No sandbox traffic/envd access token is sent to the browser.

## State and recovery

The SQL repository has a partial unique index covering provisioning, running and cleanup-pending sessions, so one user cannot create a second active resource while the first still needs cleanup. Operations use a 45-second database lease, renew it every ten seconds, and fence writes against lease ownership and concurrent stop requests. The deployment also runs one control-plane instance; this prevents a second process from treating a live provision as an abandoned one. PostgreSQL timestamps govern leases. PGlite is suitable for a single process with durable local storage.

Creation persists the session before requesting a VM, then durably journals a `pending` attempt and uncertainty deadline before the external create call. Lease-fenced outcomes distinguish `not_created`, `unknown`, and `created`, with fixed safe reason codes. E2B metadata includes the session ID; the returned VM ID is retained in the attempt journal and session before any clone/setup command. If creation succeeded but recording the native preview credential failed, the adapter preserves that known VM ID for cleanup even when its immediate kill attempt failed. A definite no-request outcome or a recorded created resource can finish cleanup after the normal credential/discovery/absence checks without waiting through the ambiguous-create window. Every throw from the E2B SDK create call remains `unknown`: status-like error fields and SDK error classes do not prove that no VM was created. Reconciliation never replays a create attempt. Creation has a 60-second request timeout, automatic create retries disabled, and an initial provider TTL bounded by the session's original one-hour deadline. The provider timeout action is explicitly kill with auto-resume disabled. Preparation commands have explicit deadlines and checked exit codes.

On startup, an abandoned provision goes into cleanup rather than replaying login/token creation. Recovery lists every provider page for matching session metadata, including paused VMs, and destroys every discovered resource. When a create response was lost and no VM ID was persisted, cleanup remains pending until the original TTL plus a two-minute request/transport cushion, then requires a successful metadata discovery showing no surviving resource. Nominal TTL expiry alone is never confirmed deletion. A discovery/API failure keeps cleanup pending; a provider without discovery cannot resolve an ambiguous create automatically. This conservative case can block a new session for roughly an hour. Operators should inspect matching `ephemeral_session_id` metadata in the E2B dashboard during a provider incident. For a stopped control plane, the restricted [operator recovery CLI](OPERATOR-RECOVERY.md) provides offline diagnostics and an audited, explicitly confirmed retry for one abandoned provision or pending cleanup; it never accepts a manual assertion as deletion evidence.

Stop and expiry first mark cleanup pending and disable the gateway. Cleanup revokes all GitHub tokens, kills workspace-user processes (including Codex/tmux and token refresh jobs), attempts Codex logout/removal of local auth, destroys the VM, and checks provider existence. Credential revocation and provider failures are persisted and retried by reconciliation; there is no successful terminal state until gateway/GitHub cleanup and VM absence are confirmed. When the VM was already gone, explicit local logout is marked not applicable. When logout failed but VM deletion succeeded, the event records that logout was unconfirmed and local credentials were destroyed with the VM.

Codex cleanup uses a bounded, read-only sandbox detail lookup and constructs a local SDK client only after verifying identity, running state, auto-resume disabled, and remaining lifetime. It does not call `Sandbox.connect`, resume the VM, or extend its timeout. Paused, expired, or unverifiable resources skip process commands and continue through destruction and absence verification.

Codex **remote account authorization revocation remains unverified**. `codex logout` and VM destruction cannot prove that OpenAI revoked all server-side refresh/device grants. The session exposes this limitation explicitly. Provider deletion likewise confirms the E2B API's resource absence; it is not a claim about physical storage sanitization beyond the provider's guarantees.

With `SESSION_MAX_HOURS=4`, extensions require an explicit user action, add 1–60 minutes at a time, and cannot exceed four hours from creation. With `SESSION_MAX_HOURS=1`, extension requests are rejected before calling the provider. The new deadline is recorded before setting provider timeout; if the provider rejects the extension, the previous deadline is restored. Server shutdown drains tracked work within a 25-second application budget and an independent 30-second process deadline, while preserving active VMs for reconciliation on restart. An incomplete drain retains local database ownership for inspection. Browser or server disconnection never extends the deadline.

Primary panes retain their exited state. An explicit **Recover shell** checks current session and repository access, then respawns a stopped pane or recreates an absent primary tmux session with a fresh login Bash shell. It never kills a living primary pane, restarts Codex automatically, copies credentials, or changes the VM timeout. Missing-server diagnostics establish absence; permission and transport failures leave status unknown. PTY completion and periodic pane inspection detect ended terminals, including retained dead panes whose tmux client remains alive. Browser connections use 30-second ping intervals and terminate after a missed matching pong at the next interval.

Input uses bounded queues and sequence acknowledgements after successful provider writes. The browser sends at most 8 KiB per input frame and keeps one frame unacknowledged; both browser and server have a 256 KiB input budget. The server accepts frames up to 32 KiB, coalesces pending input, and preserves resize ordering. Reconnect never resends uncertain writes. Shell lifecycle operations serialize per session, with limits of eight admitted requests per session and 32 overall, so a slow workspace does not occupy another session's queue.

## Validation and live acceptance

`tests/lifecycle.test.ts` exercises real PGlite migrations/indexes/leases with injected provider failures: competing creators, preparation failure, stop during create, startup recovery, ambiguous orphan discovery, expiry, extension limits/failure, failed revocation, failed VM destruction, and stale-worker fencing. E2B adapter tests verify SDK creation options and that network errors cannot become deletion confirmation. These checks do not substitute for a live provider smoke test.

Before enabling invites, use a disposable test repository to verify a real template create, browser reconnect to the same tmux/Codex session, fresh device login, gateway clone/push restrictions, successful PR creation, explicit extension, expiry, and stop. Check that the VM is absent from the provider and old gateway/GitHub credentials are rejected. Interrupt the server during creation and cleanup, restart it, and verify metadata discovery and durable cleanup. A provider outage must show pending/failed cleanup rather than completed cleanup. No live E2B template, account sign-in, or provider billing operation was performed by the local unit tests.

## Protected application preview gateway

New sessions install a root-owned, credential-stripping HTTP/WebSocket gateway on port 49152 before repository checkout, setup, or Codex. Source and readiness files are private to root. Provisioning validates the Node executable and every ancestor, rejects symlinks and non-root owners, and removes group/world write permission from operator-image Node paths before launch. The live image shipped `/usr/local`, its bin directory, and Node with mode 777; the protected startup changes those paths to 755. Global installs into those shared paths may need a user-owned npm prefix; repository-local installs are unaffected. Provisioning fails closed if these checks fail.

The native E2B ingress token is captured only at creation and encrypted in a separate server-side vault using the stable encryption key. Read-only sandbox detail requests verify running state and exact session, user, repository, branch, private ingress, and gateway metadata. Preview resolution never calls connect/resume or changes TTL. The credential never reaches a browser or the selected application: E2B authenticates ingress, then the root gateway strips it before forwarding to the selected loopback port. The separate browser viewer also strips cookies and account headers. Confirmed destruction removes the vault entry; startup reconciliation prunes obsolete entries.

The gateway is required because the inspected [E2B runtime proxy source](https://github.com/e2b-dev/runtime/blob/50fc41af77ff0877d4224e5e4ded5e7f308b5476/packages/shared/pkg/proxy/pool/client.go) forwards native authentication headers upstream. Directly proxying to user application code would reveal that credential. See the [live verification](VALIDATION.md).
