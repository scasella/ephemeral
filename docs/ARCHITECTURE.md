# Architecture and failure model

## Components

- **React + xterm frontend:** repositories, sessions, launch/stop/extend, terminal, lifecycle events, and credential cleanup status. No secrets are accepted in the UI.
- **Node/Express control plane:** GitHub OAuth, invite allowlist, same-origin mutation checks, owner-scoped APIs, WebSocket relay, and a five-second reconciliation loop.
- **PostgreSQL:** durable session state, worker leases, browser login records, encrypted upstream GitHub tokens, hashed gateway capabilities, and issuance uncertainty. Local preview uses PGlite, an embedded PostgreSQL implementation.
- **E2B provider:** one fresh VM per session, a bounded provider timeout, metadata for recovery, isolated Codex credential storage, and tmux-backed PTY reconnection.
- **Git gateway:** authenticated Git smart HTTP backed by a temporary bare repository. A server-owned pre-receive hook allows only one fast-forward update to the assigned session branch. It checks session authorization again and forwards the push upstream before accepting the local ref update. There is no arbitrary GitHub REST forwarding.

Only one control-plane process is supported. PostgreSQL advisory locking or a local file lock enforces that constraint. Worker leases protect state writes; they do not make the deployment horizontally scalable.

Local database startup refuses every existing `control-plane.lock`, including a stale or incomplete file. Graceful shutdown removes the lock; after a crash, inspect the recorded process and verify no control plane uses that data directory before manually removing it. Automatic stale-lock deletion could race with another starter and defeat exclusive ownership. Managed PostgreSQL uses its connection-scoped advisory lock instead.

The PostgreSQL singleton lock belongs to a dedicated connection for the lifetime of the control plane. The connection must have session affinity; transaction-pooling proxies are unsupported. Losing that connection permanently rejects new database calls and initiates controlled shutdown; the running process never reacquires ownership. Errors on ordinary idle query connections are handled by the pool, which discards those connections and can create replacements. Connections have a three-second acquisition timeout, five-second server statement timeout, 5.5-second client query timeout and TCP keepalive enabled.

Database close rejects new calls immediately and drains existing calls before releasing ownership. Both draining and closing have six-second bounds. Application shutdown has a 25-second deadline; the process has an independent 30-second exit deadline. Graceful shutdown preserves active VMs for reconciliation on restart. If application work does not drain, database close is skipped; if PGlite does not close safely, its lock remains for operator inspection after forced exit.

## Trust boundaries

OAuth admission is bounded before database or upstream work. Start requests allow ten per TCP peer and one hundred globally per ten-minute window, with four active globally and two per peer. Callbacks have an independent thirty-per-peer and one-hundred-twenty-global allowance per minute, with eight active globally and two per peer. Both registries hold at most 256 peers and reject excess work immediately; an in-flight slot remains held until the underlying operation settles. Peer identity comes from the socket, so forwarded headers cannot bypass admission and tunnel/proxy clients may share limits. OAuth state remains one-use and browser-bound. Expiry indexes and bounded scheduled pruning replace per-start deletion scans.

API JSON uses a 256 KiB byte limit, including after decompression, and UTF-8 encoding. This covers the maximum PR text even when each accepted Unicode code point is represented by a JSON surrogate escape pair. Oversized requests return a fixed 413 response; invalid JSON returns 400 and unsupported encoding returns 415. Label validation rejects control characters and malformed Unicode before persistence, while retaining ordinary Unicode and existing trimming/length rules.

The VM is an untrusted execution environment. Repository code and the developer can read its scoped gateway capability and their Codex login credentials. They cannot read the E2B API key, GitHub App private key, GitHub installation tokens, OAuth client secret, or encryption key from the control plane.

The browser gets an opaque HttpOnly session cookie. Its raw cookie token is hashed in storage. Browser API mutations require a custom header and a same-origin check; WebSocket upgrades require an exact Origin match and session ownership. GitHub OAuth state is one-use, time-limited, and bound to a separate HttpOnly browser cookie. The invite allowlist uses immutable numeric GitHub IDs.

Terminal attachment, input, resize and periodic checks verify browser identity, ownership and current running-session identity. Repository permission checks coalesce across attachments and cache success for at most five seconds, scoped to the browser, repository and VM identity. Browser/lifecycle checks remain fresh. A failed permission check invalidates the session cache and closes its attachments; revoked or shutdown checks cannot be revived by a late response. Permission changes are detected after the cache, polling interval and bounded upstream request latency. Extensions perform fresh repository authorization inside the lifecycle lease and recheck the session before changing its deadline. Stop and cleanup remain available after repository access is lost. HTTP responses expose explicit application-owned error types; arbitrary exception text is replaced with a fixed message.

GitHub repository selection is derived from the intersection of the user's App installations and repository permissions. Session creation checks that selection again. The gateway rechecks the user's current repository write access, session state, capability status, and expiry. Upstream installation tokens are scoped to the selected repository and encrypted with authenticated encryption at rest.

The gateway does not promise that GitHub rules permit a push. Branch protection or repository policy can reject it, and that rejection is returned to the Git client. The session cannot push other branches, delete its branch, force-rewrite its history, or call merge APIs through the gateway. The developer's own independently supplied credentials are outside this boundary.

## Lifecycle

`provisioning → running → cleanup_pending → ended`

Provisioning or sandbox loss may finish as `failed` after cleanup, retaining a safe error message. A partial cleanup remains `cleanup_pending`; retry does not report success until each required phase confirms it. New sessions are blocked while the user's previous session has active or unresolved resources.

The control plane persists external resource identity before preparing the machine. Before external creation it records an uncertainty window. A crash or timeout triggers discovery by session metadata; unknown or unconfirmed resources remain pending rather than being silently forgotten. E2B's initial bounded timeout is an independent backstop.

Gateway access is disabled before teardown proceeds. GitHub token issuance and rotation are tracked independently so previously issued tokens remain retryable. Ambiguous issuance must not be reported as successful revocation. Credentials remain encrypted until revocation or upstream expiry establishes they are no longer usable.

VM deletion and removal of local Codex credentials are separate from remote revocation of ChatGPT authorization. `codexRemoteRevocation` is always `unverified` in this implementation. Ended status confirms compute and gateway/GitHub cleanup; it does **not** assert that an extracted ChatGPT token has been invalidated remotely.

The expiry clock starts at the session request and includes provisioning. New sessions start with one hour. `SESSION_MAX_HOURS=1` is the default and matches E2B Hobby; extensions are rejected. An operator can explicitly configure `SESSION_MAX_HOURS=4` with E2B Pro to permit 30-minute extensions up to four hours from creation. The server exposes its configured limit through bootstrap, while each session records its own maximum expiry. Extension updates durable intent and requests a provider timeout adjustment. Browser or server disconnection does not end a session; expiry and reconciliation do.

Reconciliation selects `provisioning`, `running`, and `cleanup_pending` rows in SQL using a partial state index; historical rows remain available to the session-history API. Failed health probes and incomplete cleanup persist independent retry metadata outside the Session JSON. Automatic retries start at five seconds and double to a five-minute maximum, with capped attempt counts. Successful health checks or completed cleanup clear the schedule. Retry updates and worker events require the current database lease and appropriate lifecycle state. Health probe failures emit no retry events; cleanup records one sanitized retry transition per episode. Explicit stop, cleanup retry, and offline operator reconciliation bypass the automatic delay. Expiry disables access even while a health probe is in flight. Backoff never proves deletion, revocation, or noncreation.

The owner-scoped `GET /api/sessions/:id/events` endpoint returns `{ events, nextCursor }`, with 50 events by default and an explicit `limit` of 1–100. `before` is a bounded, versioned, session-bound cursor over the exact PostgreSQL `(at,id)` key; cursor timestamps retain six fractional digits rather than round through JavaScript dates. SQL fetches newest-first with `LIMIT + 1`, then returns each selected page in chronological order. The matching `(session_id,at,id)` index avoids offset scans. The internal legacy `events()` accessor returns at most the latest 100 events. Activity retains only one page, fences requests by account/session, pauses polling on older pages, and preserves the prior page after errors without presenting it as current. Events are not purged by pagination.

## Repository setup

Setup runs only on an explicit user request. A saved recipe belongs to one authenticated user and numeric repository ID; each edit creates a new version without executing it. Run requests require the reviewed version and retain an immutable recipe snapshot. Recipes survive session replacement, while runs stay attached to their original session in separate tables. Setup writes do not modify lifecycle state or worker leases.

Owner checks protect every mutation; saving or starting setup also requires current GitHub authorization. Cancellation uses local ownership checks so an unavailable authorization service does not prevent stopping a run. Execution requires a running, unexpired session and read-only VM identity verification; it never resumes a paused VM or extends its lifetime. Commands run as the ordinary workspace `user` with the terminal's filesystem, network, scoped Git capability, and developer credentials. The 5–600 second timeout is capped by remaining session time and sent as an absolute deadline. An independent VM wrapper reserves cleanup time and kills ordinary process-group children before reporting completion. This is not containment against hostile code that deliberately detaches or interferes with another process of the same user; VM expiry and deletion remain the outer boundary.

Only one execution or unresolved execution hold is allowed per session. Setup mutations serialize within each session, with at most eight requests per session and 32 requests in total, so a slow authorization check does not block unrelated sessions. The controller reserves up to eight locally owned executions before inserting their records; unresolved remote holds still block their original sessions after local execution work settles. A failure confirmed before provider invocation records that execution did not start, releases its hold, and permits an explicit retry. Cancellation, session stop, expiry, access loss, persistence failure, timeout, and server shutdown retain distinct reasons; only a user cancellation is attributed to the user. Cancellation and timeout results require confirmed group cleanup. Missing confirmation after invocation marks the run interrupted and retains its hold through the original deadline plus cleanup grace. Shutdown requests termination, waits for bounded execution work to settle, and never replays commands. Restart releases only queued records explicitly marked as not invoked; running records and legacy queued records remain interrupted and held conservatively. Neither is replayed automatically. Failed final persistence retains local ownership and the bounded snapshot; reads, later run requests, and a background retry save it after database recovery. Existing records without invocation or reason fields remain readable without inferring that a user cancelled them.

The browser polls durable status and output. New runs retain at most 64 KiB of redacted output, including its beginning and end with a marker for the omitted middle. An optional retention-format field distinguishes these runs from older records that retained only the beginning. The final buffered tail is persisted when execution finishes; live output can lag while incomplete lines are screened. Retention and transport remain bounded even for commands that continuously emit output. The VM snapshots known environment credentials and token/API-key values from its bounded, owned, nonsymlink Codex auth file before execution; an unsafe or unreadable existing file prevents setup launch. It masks those values before transport. Both the VM and control plane strip terminal controls across chunks and mask common credential formats, quoted auth fields, URI credentials and PEM blocks before clipping. Incomplete lines remain buffered until newline or completion; an overlong unfinished line is omitted as a unit so clipping cannot persist a credential fragment. These checks cannot identify every application secret or changes to credential values during execution. They apply only to retained setup output; recipe commands remain intact and interactive terminals keep their ordinary byte stream. Recipes and output are stored, so users must avoid embedded or printed secrets. Preview explicitly simulates the workflow and never executes submitted commands on the host.

Workspace inspection uses a temporary Git metadata directory with fixed settings and a pinned HEAD, a copied index of at most 16 MiB, and local attributes/excludes files of at most 64 KiB each. Source metadata is checked again before returning the snapshot, and temporary metadata is removed on completion or failure. Repository configuration is not used for worktree inspection, preventing configured filters, textconv, external diff, hooks and fsmonitor commands from running. Repository .gitignore and local info/exclude rules remain effective. Custom/global Git settings are not reproduced; unsupported metadata, including some split-index layouts, can produce an unknown observation.

Explicit safe eol=lf/crlf attributes with canonical LF HEAD text can normalize CRLF for the displayed comparison. Mixed endings, lone carriage returns and unsupported filter, encoding, ident or diff attributes stay raw, with visible provenance. Both review surfaces mark hidden/bidi controls, and identity fields additionally mark line breaks, tabs and concealed ASCII spaces, without altering opaque path keys or requests, preserve ordinary international text and contextual joining/variation sequences, and bound display expansion to one text node per field. These markers help review; they do not establish that code is safe.

## Verification boundaries

Automated tests exercise the state machine with real PostgreSQL semantics through PGlite and injectable cloud providers, credential encryption/tampering, active-session uniqueness, cleanup failures, owner authorization, CSRF and WebSocket Origin rejection. Git tests exercise the actual pre-receive hook with local temporary repositories.

Security regressions cross the actual terminal upgrade and idle polling paths, real browser-session authorization and OAuth state consumption, and Git gateway request admission. Independent cleanup tests keep gateway and GitHub failure conditions separate. Disposable-copy mutation probes verify that bypassing ownership, Origin, periodic permission checks, fresh extension authorization, cleanup completeness, hook authorization, push leases, capability binding, body limits or credential context causes relevant assertions to fail. These probes use synthetic credentials and local fixtures.

These tests do not prove live E2B credentials, template provisioning, GitHub App permissions, Codex device login, or an HTTPS production proxy are configured correctly. Before inviting users, run an end-to-end disposable repository smoke test: launch, authenticate Codex, commit/push the allowed branch, reject a push to another branch, open a draft PR, reconnect the terminal, verify Hobby rejects extensions (or test an explicitly configured Pro extension), stop, and verify provider absence plus upstream token rejection. Repeat with forced provisioning and cleanup failures.

The [Render deployment guide](DEPLOYMENT.md) describes the local Blueprint and live acceptance checklist. Render deployment and live E2B/GitHub/Codex behavior remain unverified. The planned attached service disk ensures Render stops the old process before starting a replacement, including when durable state is in managed PostgreSQL.

## Private application viewer

The control plane authorizes a single selected development port and issues a one-use 60-second POST handoff to a different viewer hostname for every access generation. The hostname is `<generation-uuid>.<configured-base-host>`; the base host itself serves no application. The handoff becomes a host-only HttpOnly cookie bound to that host, originating browser login, owner, session, generation, and the earlier of ten minutes or session/login expiry. HTTP, WebSocket, and one-use handoff consumption must match the generation in the Host. Tokens are never in URLs; only hashes persist. Enabling or replacing generates a fresh access generation and browser origin, so an already loaded old application cannot inherit a later generation's cookie. Closing preview preserves workspace processes. Session stop/expiry and browser logout invalidate grants; WebSockets recheck local state every two seconds, and explicit close/stop immediately signals connected viewers.

Every HTTP request verifies browser/session fences and repository authorization. Repository verification alone is shared for at most ten seconds, with a bounded cache and no cached failures; control-plane preview mutations perform fresh checks. Encrypted native ingress credentials are independent of Session JSON. The viewer resolves only the fixed protected gateway for the exact VM, which strips native credentials before forwarding to the selected app. Requests and responses have fixed bounds, and the viewer exposes no account APIs. Browser policy blocks framing, workers, cross-origin application connections and external redirects. Hosting requires a separate base DNS namespace with wildcard HTTPS routing; explicit local-only configuration permits a `localhost` base with generation-specific loopback hosts and matching listener port. See [release migration](RELEASE.md#private-preview-migration).
